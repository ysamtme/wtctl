# Подключения и права

Подключение — это адрес сервера, учётная запись и права клиента. Задаётся оно файлом JSON или переменными окружения. Одно и то же подключение читают MCP-сервер, CLI и SDK.

В примерах команда пишется как `wtctl`. Без установленного CLI это `npx -y wtctl`, см. [cli.md](cli.md#установка).

## Создание подключения

```shell
wtctl config init
```

Команда спросит адрес сервера, логин и пароль и запишет подключение в `~/.wtctl/connections.json` (в Windows это `C:\Users\ИМЯ\.wtctl\connections.json`). Первое подключение становится подключением по умолчанию.

| Параметр | Что делает |
| --- | --- |
| `--name ИМЯ` | имя подключения; так добавляется второй сервер |
| `--allow-write`, `--allow-execute` | включить запись и выполнение кода, см. [права](#права) |
| `--url АДРЕС`, `--username ЛОГИН` | адрес и логин параметрами, без вопросов в терминале |
| `--password-stdin` | прочитать пароль из stdin |
| `--password-env ИМЯ` | записать в файл не пароль, а имя переменной окружения, в которой он лежит |
| `--force` | заменить подключение с тем же именем |

В аргументах команд пароль не передаётся.

Логин и пароль уходят на сервер в каждом запросе. Если сервер на другом компьютере, нужен адрес `https://`.

## Проверка подключения

```shell
wtctl status
```

`status` показывает версию сервера и права подключения:

```json
{
  "ok": true,
  "data": {
    "connection": "default",
    "baseUrl": "http://localhost:8088/",
    "version": "2025.2.1535",
    "database": "mssql",
    "userId": "0x5555555555555501",
    "permissions": { "write": false, "execute": false }
  }
}
```

Здесь и дальше ответы показаны с отступами и без служебных полей. CLI печатает ответ одной строкой.

```shell
wtctl check
```

`check` идёт по шагам: вход, версия, сведения о сервере, запрос к каталогу, чтение документа, поля типа, названия полей, библиотеки, логи, портал, выполнение кода. На сервер он ничего не пишет. Шаг с выполнением кода пропускается, если у подключения нет права `execute`.

```json
{
  "ok": true,
  "data": {
    "version": "2025.2.1535",
    "permissions": { "write": true, "execute": true },
    "checks": [
      { "name": "login", "result": "ok" },
      { "name": "version", "result": "ok" },
      …
      { "name": "execute", "result": "ok" }
    ],
    "summary": { "ok": 11, "failed": 0, "skipped": 0 }
  }
}
```

У шага, который не прошёл, в `reason` написана причина. Если другие команды отвечают ошибками, `check` покажет, на каком шаге проблема. Частые отказы разобраны в [installation.md](installation.md#если-не-получилось).

## Откуда берётся подключение

Клиент ищет подключение в таком порядке:

1. файл из `--config` или из переменной `WTCTL_CONFIG`;
2. переменные окружения, если задана `WTCTL_URL`;
3. файл `~/.wtctl/connections.json`, если он есть.

Если ничего из этого нет, придёт `NOT_CONFIGURED` с подсказкой, что задать. Какой файл читает CLI, покажет `wtctl config path`.

## Файл подключений

```json
{
  "defaultConnection": "test",
  "connections": {
    "test": {
      "baseUrl": "http://localhost:8088",
      "usernameEnv": "WTCTL_TEST_USERNAME",
      "passwordEnv": "WTCTL_TEST_PASSWORD",
      "permissions": { "write": true, "execute": true }
    },
    "production": {
      "baseUrl": "https://hcm.example.com",
      "usernameEnv": "WTCTL_PROD_USERNAME",
      "passwordEnv": "WTCTL_PROD_PASSWORD",
      "permissions": { "write": false, "execute": false }
    }
  }
}
```

Подключение из файла выбирается так: `wtctl --connection production …` или переменной `WTCTL_CONNECTION`. Если не указать ни то ни другое, берётся `defaultConnection`. Другой файл — `--config connections.json`. Пример без секретов печатает `wtctl config example`; готовый файл — [connections.example.json](../examples/connections.example.json).

Файл — JSON в UTF-8 размером до 1 МБ.

| Поле | Значение | По умолчанию |
| --- | --- | --- |
| `baseUrl` | адрес сервера, `http://` или `https://`; обязателен | — |
| `usernameEnv`, `passwordEnv` | имена переменных окружения с логином и паролем | — |
| `username`, `password` | логин и пароль прямо в файле | — |
| `permissions.write` | разрешить запись | `false` |
| `permissions.execute` | разрешить код, функции библиотек и запросы XQuery | `false` |
| `timeoutMs` | таймаут одного запроса к серверу, мс | 30000 |
| `maxResponseBytes` | предел размера ответа сервера | 32 МБ |
| `outputLimitBytes` | предел размера ответа одной операции; ответ больше сохраняется локально | 24 КБ |
| `runtimeDir` | папка для сохранённых результатов | `~/.wtctl/runtime` |

Пароль лучше держать в переменной окружения. Если он записан в файле, файл не должен попасть в git. Для разового запуска есть `--password-stdin`: пароль читается из stdin.

## Переменные окружения

Без файла подключение собирается из переменных:

| Переменная | Значение |
| --- | --- |
| `WTCTL_URL` | адрес сервера |
| `WTCTL_USERNAME`, `WTCTL_PASSWORD` | логин и пароль |
| `WTCTL_ALLOW_WRITE`, `WTCTL_ALLOW_EXECUTE` | `true` разрешает запись и выполнение |
| `WTCTL_TIMEOUT_MS` | таймаут запроса |
| `WTCTL_RUNTIME_DIR` | папка для сохранённых результатов |
| `WTCTL_HOME` | папка клиента вместо `~/.wtctl`: в ней файл подключений и сохранённые результаты |

Когда в файле есть раздел `connections`, адрес, учётная запись и права берутся только из выбранного подключения. Общие `WTCTL_URL`, `WTCTL_USERNAME`, `WTCTL_PASSWORD`, `WTCTL_ALLOW_WRITE` и `WTCTL_ALLOW_EXECUTE` на него не действуют — чтобы оставшаяся в окружении переменная не подменила сервер или права. `WTCTL_TIMEOUT_MS` и `WTCTL_RUNTIME_DIR` действуют всегда.

## Права

У подключения два права, оба по умолчанию выключены.

| Право | Что разрешает |
| --- | --- |
| — | чтение: поиск, документы, поля, логи, файлы |
| `write` | создание, правку и удаление объектов и файлов |
| `execute` | код на сервере, функции библиотек, запросы XQuery |

Код и функции библиотек тоже могут менять данные, поэтому `execute` без `write` — не «только чтение».

Эти права ограничивают сам клиент. Больше, чем разрешено учётной записи на сервере, они не дадут.

Как включить:

- при создании подключения: `wtctl config init --allow-write --allow-execute`;
- у готового подключения: поправить `permissions` в файле подключений или создать подключение заново с `--force`;
- без файла: переменные `WTCTL_ALLOW_WRITE=true` и `WTCTL_ALLOW_EXECUTE=true`.

MCP-сервер читает подключение при запуске. Новые права он увидит после перезапуска: в новом чате или после перезапуска приложения.

На боевом сервере `write` и `execute` стоит включать, только когда они нужны. Как выглядит отказ и как понять, прошла ли запись, написано в [security.md](security.md).

## Сохранённые результаты

Ответ больше `outputLimitBytes` клиент не отдаёт целиком, а сохраняет в `runtimeDir`. В ответе вместо данных приходят:

- `meta.truncated` и `meta.resultId` — ID сохранённого результата;
- `meta.resultBytes` — его размер;
- `data.preview` — начало данных.

По этому ID данные дочитываются частями, без нового запроса к серверу:

| Интерфейс | Прочитать часть | Сохранить в файл |
| --- | --- | --- |
| MCP | `hcm_result_read` | `hcm_result_export` |
| CLI | `wtctl result read ID` | `wtctl result export ID --to ФАЙЛ` |
| SDK | `readResult` | `exportResult` |

Список из ответа (`items`, `types`, `fields`, шаги пакета) читается по элементам и выгружается по строке на элемент: `--format jsonl`. Сохранённый текст (лог, файл сервера) читается и выгружается текстом: `--format text`.

В `runtimeDir` лежат данные с сервера, в том числе персональные. Папка не должна быть доступна другим и не должна попадать в git. Клиент её не чистит: старые результаты удаляются вручную.

## Ограничения ввода

- Файл или stdin команды — до 8 МБ.
- Код для выполнения — до 1 МБ.
- Загрузка файла одним вызовом — до 8 МБ; файл крупнее загружается частями.

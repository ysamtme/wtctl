# Логи сервера

Клиент читает логи сервера через его же API. Доступ к диску сервера не нужен, права `write` и `execute` — тоже.

Главный лог — `xhttp_ГГГГ-ММ-ДД.log`. Сюда сервер пишет отказы, ошибки запросов и ошибки кода. Когда сервер отказывает, в самом ответе причины нет, поэтому причину нужно искать в логе. Строка может быть короткой («Элемент не найден»), а после ошибки в тексте запроса XQuery её может не быть вовсе.

Что лежит в каком логе и как искать причину отказа, описано в теме гайда: [logs.md](../skills/wtctl/references/logs.md).

## Команды

```shell
wtctl logs list --type xhttp
wtctl logs search xhttp_2026-10-01.log --level error --limit 5
wtctl logs search xhttp_2026-10-01.log --text "XQUERY FAILED"
wtctl logs read xhttp_2026-10-01.log
wtctl logs follow xhttp_2026-10-01.log
```

| Команда | Инструмент MCP | Метод SDK | Что делает |
| --- | --- | --- | --- |
| `logs list` | `hcm_logs_list` | `listLogs` | файлы: имя, тип, дата, размер в байтах; сначала новые, 30 на странице |
| `logs search` | `hcm_logs_search` | `searchLogs` | события по тексту, уровню, метке потока |
| `logs read`, `logs tail` | `hcm_log_read` | `readLog` | текст файла |
| `logs follow` | `hcm_log_follow` | `followLog` | события, появившиеся с прошлого вызова |

## Как это работает

- Тип лога в списке — это имя файла без даты: `xhttp`, `xhttp_middleware`, `agent`.
- `read` без аргументов отдаёт конец файла — столько, сколько помещается в один ответ. `--tail-bytes N` берёт больше, `--full` — весь файл. Большой текст сохраняется локально, см. [configuration.md](configuration.md#сохранённые-результаты): `result read ID` читает его частями как текст, `result export ID --to ФАЙЛ --format text` сохраняет в файл.
- `search` ищет в последних 512 КБ файла; `--full` ищет по всему файлу. Многострочное событие со стеком вызовов приходит целиком. Пока в ответе есть `nextOffset`, совпадения не кончились: нужен повтор с `--offset` и `--expected-fingerprint` из ответа.
- Уровень события (`error`, `warning` и другие) клиент определяет по словам в тексте, русским и английским, приблизительно. Если поиск по уровню ничего не нашёл, нужно искать по тексту.
- После каждой записи в лог сервер около пяти секунд не отдаёт этот файл. Клиент пережидает сам: перед чтением, если только что получил от сервера отказ, и перед повтором, если сервер файл не отдал (повтор один). Поэтому чтение лога сразу после отказа занимает около шести секунд.
- `follow` делает один опрос. Первый вызов отдаёт последние 10 событий и `cursor`; следующий вызов с этим `cursor` отдаёт то, что появилось с тех пор. `omitted` — сколько новых событий не поместилось в ответ; `gapPossible:true` — часть событий могла быть пропущена.
- Дата и время в логе — время сервера. Каждый день сервер начинает новый файл.

## Ошибки

| Код | Что случилось |
| --- | --- |
| `LOG_NOT_FOUND` | файла с таким именем нет в списке |
| `LOG_READ_UNAVAILABLE` | сервер не отдал текст файла и со второй попытки: в лог постоянно что-то пишется. Повторить через десять секунд или взять лог за прошлую дату |
| `LOG_CHANGED` | файл изменился между страницами поиска; поиск нужно начать заново |
| `INVALID_LOG_CURSOR` | `cursor` испорчен или от другого файла; `follow` нужно начать без него |

Если сервер не отдал лог, клиент не пытается достать его другим путём.

В логах бывают персональные данные и адреса. С прочитанным нужно обращаться так же, как с остальными данными сервера.

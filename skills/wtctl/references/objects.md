# Объекты: поля, чтение, создание, правка, удаление

## Поля типа

`hcm_schema {type:"collaborator"}` показывает верхний уровень, до 80 полей на странице (`cursor: nextCursor` — дальше).

| Аргумент | Что делает |
| --- | --- |
| `search:"логин"` | ищет слова в пути, заголовке и имени каталога, на который поле ссылается (`search:"subdivisions"`), на любой глубине; все слова должны быть в одном поле |
| `path:"access"` | показывает поля внутри структуры; саму структуру описывает `element` в ответе: список ли это (`multiple`) и какой у элемента ключ (`key`) |
| `deep:true` | показывает вложенные поля всех уровней одним списком; вместе с `path` — всё внутри этой структуры. Страницы те же: `total`, `nextCursor`; `cutBySize` — страница короче запрошенной, больше в ответ не помещается. Страница схемы не больше 16 КБ и как большой ответ не сохраняется: всю схему собирают страницами по `nextCursor` |
| `origin:["custom"]` | только настраиваемые поля; ещё бывают `own`, `inherited`, `catalog` |
| `kind:"ID вида"` | настраиваемые поля, заданные для вида объекта |
| `include:["methods"]` | добавляет методы формы |

Пометки у поля:

- `query:true` — поле есть в каталоге, по нему ищет `hcm_query`;
- `computed:true` — значение вычисляет сервер, записать его нельзя; копии полей связанных объектов (`position_name`, `org_name`) так не помечены — о них ниже, в разделе про `resave`;
- `origin:"catalog"` — поле есть в строке каталога, а на верхнем уровне документа его нет; то же значение может лежать в документе глубже (`access_level` строки — `access.access_level` документа), это покажет `hcm_schema {type, search:"имя"}`;
- `references:"groups"` — в поле лежит ID объекта из этого каталога;
- `references` — не всегда каталог: `common.…` и `lists.…` — список, в поле лежит ID его элемента; выражение сервера (`DefaultDb.GetOptCatalog(…)`, `tools.get_list_lngs()`) — на что ссылается поле, зависит от других данных. Элементы списка читает `hcm_xquery {query:"for $e in common.event_types return $e"}`: `id` — значение для поля, `name` — название. У строкового поля без `references` списка значений в форме нет: посмотри, что лежит у существующих объектов;
- рядом со ссылкой каталог обычно хранит и название: `position_id` → `position_name`, `position_parent_id` → `position_parent_name`, `org_id` → `org_name`. Соединять каталоги ради названия не нужно;
- `children:N` — структура: её поля показывает `path`, все вложенные сразу — `deep:true`;
- `multiple:true` — список элементов;
- `required:true` — при создании поле можно не передавать: сервер подставит значение по умолчанию (`type_id` мероприятия станет `one_time`, `access.access_role` сотрудника — `user`, логическое поле — `"0"`). У настраиваемого поля (`origin:"custom"`) это пометка «обязательное» из его настройки: значение передай сам.

Если `hcm_types` показывает у типа `customFields:"by kind"`, настраиваемые поля зависят от вида объекта: передай `kind`. Какое поле хранит вид, сказано в `notes`.

## Чтение

`hcm_object_get {id:"0x…", fields:["login","lastname"]}`. Без `fields` приходит весь документ. Ответ: `{ok, data:{id, type, url, data, fingerprint}}` — поля документа лежат в `data.data`. `fields` выбирает только поля верхнего уровня. `url` — адрес документа: чтение, правка и удаление принимают его вместо `id`.

- Пустых полей в `data.data` нет: запрошенное поле без значения названо в `emptyFields`. Если запрошенного поля у типа нет вовсе, оно названо в `unknownFields`: сверь имя с `hcm_schema`.
- Поле, которое сервер вычисляет только для каталога (`fullname` у сотрудника), в документе не хранится. Запрошенное в `fields`, оно приходит отдельно — в `fromCatalog`.
- Несколько объектов за один вызов: `hcm_object_get {ids:["0x…","0x…"], fields:["name"]}`, до 100. Ответ — `items` в порядке `ids`, в каждом элементе `id`, `type`, `url` и документ в `data`. Объект, который не прочитан, остальных не останавливает: в его элементе `id` и `error`, в ответе `failed` — сколько таких. Ответ, который не поместился, сохраняет в файл `hcm_result_export`.
- Повторяемый элемент (`multiple:true` в схеме) — всегда список, даже когда элемент один: `collaborators.collaborator` — массив.
- Даты — местное время сервера, без смещения: `2026-10-02T16:42:00`. Логические поля — `"1"` и `"0"`, числа — строки.
- ID принимается в любой записи: `"0x65CCCF743BBDFFB7"` и `"7335070936043061175"` — один объект. Аргумент `type` необязателен; если он задан и не совпал, ошибка `TYPE_MISMATCH` называет настоящий тип.

## Создание

`hcm_object_create {type:"group", data:{code:"sales", name:"Отдел продаж"}}`. В ответе `id` нового объекта. ID назначает сервер, в `data` его не передают. `type` — имя типа, а не каталога: `group`, а не `groups`.

Значения по умолчанию сервер подставляет сам. Обработчики, которые админка выполняет при создании, через API не запускаются: если они заполняют что-то важное, передай эти поля сами.

Если ответ не пришёл или исход `indeterminate`, не создавай заново: сначала найди объект через `hcm_query`.

Когда ID нужен до создания, документ записывают сами (проверено на 2025.1 и 2025.2 с PostgreSQL):

1. `hcm_api_write {operationId:"native.lds.getNewObjectId", args:{dbName:"wt_data"}}` → `{"ObjectID":"7336568271880514489"}`. Это десятичная запись; тот же ID — `0x65D0B9F8F3D6EBB9`.
2. Адрес нового документа складывается из записи `0x…`: первые 14 цифр — папка, последние две — файл: `x-local://wt_data/objects/65D0B9F8F3D6EB/B9.xml`.
3. `hcm_api_write {operationId:"native.lds.putDoc", args:{url:"…", data:"<group SPXML-FORM=\"x-local://wtv/wtv_group.xmd\"><id>7336568271880514489</id><code>sales</code><name>Отдел продаж</name></group>", neverSaved:true, writeDocInfo:true}}`. В `<id>` — десятичная запись, адрес формы — `formUrl` из чтения объекта того же типа.
4. Проверить: `hcm_object_get {id:"0x65D0B9F8F3D6EBB9"}`.

## Правка

```json
{ "id": "0x65CCCF743BBDFFB7", "patch": { "name": "Новое имя", "is_hidden": true }, "remove": ["comment"], "preview": true }
```

`preview:true` показывает `changes` и ничего не записывает. Остальное содержимое документа при записи сохраняется. У поля, которого до правки не было, в `changes` нет `before`.

Правка, которая ничего не меняет, на сервер не уходит: в ответе `noop:true`. Поле, которому записано то же значение, в `changes` не попадает. У удаляемого элемента списка `before` показывает его ключ и поля.

Пути к полям:

| Что | Путь |
| --- | --- |
| поле | `name` |
| поле в структуре | `access.access_level` |
| элемент списка по номеру | `collaborators.collaborator[0].collaborator_id` |
| элемент списка по ключу | `collaborators.collaborator[collaborator_id=0x5555555555555501].collaborator_id` |
| настраиваемое поле | `custom_elems.custom_elem[name=код_поля].value` |

Запись по ключу создаёт элемент списка, если его нет; когда элементу нужен только ключ, значение повторяет ключ: `patch:{"collaborators.collaborator[collaborator_id=0x…].collaborator_id":"0x…"}` добавляет сотрудника в группу. Список целиком записывает структура-родитель, в `patch` и в `data` при создании: `{collaborators:{collaborator:[{collaborator_id:"0x…"},{collaborator_id:"0x…"}]}}`; прежние элементы при этом заменяются. Убрать все элементы — `remove:["collaborators"]`. `remove` с путём до элемента (`custom_elems.custom_elem[name=код_поля]`) удаляет элемент целиком. Значение `null` в `patch` делает поле пустым, `remove` убирает его из документа. Путь в `remove`, которому в документе ничего не соответствует, — отказ `PATCH_PATH_MISSING` с этим путём, и в предпросмотре тоже; ничего не записано, даже если другие пути вызова нашлись. Так опечатка в ключе не выглядит как «удалять нечего».

Значения: логические — `true` и `false`, ID — строкой.

Дата — строкой `"2024-05-17"` или `"2024-05-17T09:30:00"`. Это местное время сервера: смещение в значении (`Z`, `+03:00`) сервер отбрасывает и время не пересчитывает. Другую запись (`17.05.2024`, пробел вместо `T`) сервер читает неверно и сохраняет другое значение, поэтому клиент отвергает её до записи: `INVALID_ARGUMENT` с именем поля.

`expectedFingerprint` со значением `fingerprint` из чтения защищает от чужой правки: если объект с тех пор изменился, придёт `CONFLICT` и ничего не запишется. Прочитай объект заново и повтори.

Поле верхнего уровня, которого у типа нет, клиент отвергает до записи и до предпросмотра: `UNKNOWN_FIELD` называет лишние имена и похожие настоящие. Так же при создании. Вычисляемое поле (`computed:true`, например `fullname` у сотрудника) отвергается так же, с `INVALID_ARGUMENT`: меняй поля, из которых оно складывается (`lastname`, `firstname`, `middlename`).

После записи клиент перечитывает объект и сверяет поля. `READ_BACK_MISMATCH` значит, что документ сохранён, но поля из `details.fields` не приняли значение. Остальные поля запроса записаны. Обычная причина: поле вычисляемое, сервер подставил своё значение или внутри структуры нет такого поля. Проверь поле в `hcm_schema`.

## Поля, которые сервер заполняет сам

Часть полей документа — копии из связанного объекта. Сервер заполняет их в тот момент, когда сохраняют сам документ, а не когда меняется связанный объект. Записать такое поле напрямую нельзя: `READ_BACK_MISMATCH`, подсказка называет поле, которое менять вместо него. Предпросмотр называет такие поля правки в `serverFilled`. Клиент узнаёт их по коду формы, который заполняет поле перед сохранением, поэтому список бывает и лишним, и неполным: `org_id` сотрудника, который сервер берёт из должности, в нём нет.

У сотрудника это `position_name`, `position_parent_id` и `position_parent_name`: название должности `position_id` и подразделение, в котором она стоит.

Перевести сотрудника в другое подразделение:

1. В должности сотрудника записать новое подразделение: `hcm_object_patch {id:"<position_id>", patch:{parent_object_id:"<ID подразделения>"}}`.
2. Сохранить карточку сотрудника заново: `hcm_object_patch {id:"<ID сотрудника>", resave:true}`.

`resave:true` записывает документ и без правок, и сервер заполняет копии заново — в документе и в строке каталога. Без второго шага карточка и каталог `collaborators` показывают прежнее подразделение. `resave` можно задать вместе с `patch`.

В ответе правки `changes` — только твои изменения; поля, которые при сохранении изменил сам сервер, названы в `serverChanged` (имена верхнего уровня). Предпросмотр `resave` отвечает `noop:false` и пустым `changes`: что сервер заполнит заново, заранее не видно.

Принять сотрудника на должность:

1. `hcm_object_create {type:"collaborator", data:{lastname:"…", firstname:"…"}}`.
2. `hcm_object_create {type:"position", data:{name:"…", org_id:"0x…", parent_object_id:"<ID подразделения>", basic_collaborator_id:"<ID сотрудника>"}}`.
3. `hcm_object_patch {id:"<ID сотрудника>", patch:{position_id:"<ID должности>"}}` — название должности, подразделение и организацию сервер заполнит в карточке сам.

Дата приёма — поле сотрудника `hire_date`; `position_date` — другая дата, вступления в должность. Какие поля заполнены у уже работающих, покажет чтение одного из них целиком.

Не каждую копию заполняет сервер. Поля участника мероприятия `person_fullname`, `person_position_name`, `person_subdivision_name` и другие `person_…` в `collaborators.collaborator` заполняет админка в браузере: после правки через API и после `resave` они пусты и в документе, и в строке `event_collaborators`. Переданные вместе с `collaborator_id`, они сохраняются: `{collaborator_id:"0x…", person_fullname:"…"}`, значения — из строки `collaborators`.

## Удаление

`hcm_object_delete {id:"0x…", permanent:true}` удаляет безвозвратно, корзины нет. С `catalog:"groups"` клиент проверит, что объект был в каталоге и исчез из него.

Строки связанных каталогов (`group_collaborators`, `event_collaborators`, `person_hierarchys`) на части серверов после удаления остаются, см. [queries.md](queries.md): проверь их запросом до и после. Нужна копия — прочитай объект до удаления (`hcm_object_get`). Вернуть объект можно только созданием нового: документ, записанный по прежнему адресу, на PostgreSQL потом не удаляется из каталога.

`READ_BACK_MISMATCH` при удалении: сервер ответил без ошибки, но объект остался в каталоге. Что делать, говорит `hint`.

## Ошибки

| Код | Что случилось | Что делать |
| --- | --- | --- |
| `UNKNOWN_TYPE` | такого типа нет или вместо типа задан каталог | взять имя из `hint` или из `hcm_types` |
| `INVALID_ARGUMENT` с именем поля | дата записана не так, как её читает сервер | записать как `"2024-05-17"` или `"2024-05-17T09:30:00"` |
| `PLATFORM_SOAP-FAULT`, HTTP 500 при чтении | объекта с таким ID нет или это ID строки каталога без своего типа объекта: у такой строки документа нет | проверить ID через `hcm_query` |
| `TYPE_MISMATCH` | объект другого типа, чем задан в `type` | тип — в `details.actualType` |
| `CONFLICT` | объект изменился после чтения | прочитать заново |
| `IMMUTABLE_ID` | попытка изменить `id` | ID не меняется |
| `UNKNOWN_FIELD` | у типа нет поля с таким именем; ничего не записано | взять имя из `hint` или из `hcm_schema` |
| `READ_BACK_MISMATCH` | часть полей не сохранилась | см. выше |
| `WRITE_DISABLED` | запись запрещена подключением | сказать пользователю |

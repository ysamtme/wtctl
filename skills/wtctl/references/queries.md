# Поиск объектов

## Условия `hcm_query`

```json
{
  "catalog": "collaborators",
  "where": { "is_dismiss": false, "fullname": { "contains": "Иван" } },
  "fields": ["id", "fullname", "login"],
  "order": ["fullname"],
  "limit": 20
}
```

- Условия в `where` соединяются через «и».
- `поле: значение` — равенство. `поле: {оператор: значение}` — сравнение.
- Операторы: `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `contains`, `in`. Список в `in` — до 100 значений: `role_id: {in: ["admin", "user"]}`.
- Условия «начинается с» нет: формы, которая работает на обеих базах данных, сервер не даёт. Ищи через `contains` и отбирай строки по началу значения у себя.
- `order` сортирует по полям каталога: `order: ["fullname"]` или `order: ["hire_date desc", "id"]`, до пяти полей. Без `order` порядок строк сервер не обещает.
- Искать можно только по полям каталога. В `hcm_schema` у них `query:true`. По остальным полям документа каталог не ищет: ошибка `UNKNOWN_CATALOG_FIELD` называет лишние поля.
- `contains` регистр не различает. Равенство строк зависит от базы данных сервера: на MS SQL регистр не различается, на PostgreSQL различается (`login: "USER1"` найдёт `user1` только на MS SQL).
- Поле, которое в строке приходит списком (например `role_id` у ресурса), сравнивается на вхождение: `role_id: "0x5555555555555501"` находит строки, где это значение есть в списке. Оператор `ne` для таких полей не используй: базы отвечают на него по-разному. Сортировать по такому полю нельзя.

Как писать значения:

| Что | Как | Пример |
| --- | --- | --- |
| ID | строкой, `0x…` или десятичной записью | `id: "0x5555555555555501"` |
| Дата | строкой ISO, можно со временем | `hire_date: {gte: "2024-01-01"}`, `{lt: "2024-01-31T18:00:00"}` |
| Логическое | `true`, `false` | `is_dismiss: false` |
| Пустое поле | пустой строкой | `code: ""` |
| Непустое поле | `ne` с пустой строкой | `email: {ne: ""}` |

## Ответ и страницы

```json
{ "items": [{ "id": "0x5555555555555501", "fullname": "Иванов Иван Иванович" }], "total": 22, "nextStartPosition": 20 }
```

- `total` — сколько строк подходит под условие. Условия, сортировку и `limit` применяет сервер.
- `nextStartPosition` есть, пока строки не кончились. Для следующей страницы повтори вызов с теми же условиями и `startPosition`, равным этому числу.
- `incomplete:true` значит, что конец не установлен, а читать дальше нельзя; причина в `hint`. Это не «ничего не найдено».
- На странице по умолчанию 20 строк, можно до 1000. Всегда задавай `fields`: строка каталога длинная.
- Запрошенное поле без значения приходит пустой строкой, поле со списком значений — пустым списком: у всех строк одни и те же поля. Запрошенное поле, которого в каталоге нет, названо в `unknownFields`: поиск идёт по строкам каталога, остальные поля документа читает `hcm_object_get`.
- Повторяемый элемент внутри строки — всегда список.
- Логическое поле в строке — `"1"` или `"0"`, число — строка. В условии пишут `true`, `false` и число.
- Даты — местное время сервера, без смещения: `2026-10-02T16:42:00`.
- Страницы не образуют снимок: если данные меняются во время чтения, строки могут повториться или пропасть.
- Весь каталог: `order: ["id"]`, `limit` до 1000, страницы до конца по `nextStartPosition`. Затем убери повторы по `id` и сверь число строк с `total`.

## Каталоги без своего типа объекта

`hcm_types` показывает каталоги, строки которых — объекты: у строки есть документ, его читает `hcm_object_get`. На сервере есть и другие каталоги, например `group_collaborators`, `event_collaborators`, `person_hierarchys`. Их строки сервер строит сам по документам другого типа: строка `group_collaborators` появляется, когда в документ группы добавлен участник.

- Искать в таком каталоге можно как в любом: `hcm_query {catalog:"group_collaborators", where:{group_id:"0x…"}, fields:["collaborator_id"]}`.
- Поля строки показывает `hcm_schema` по имени каталога: `{type:"group_collaborators"}`. В ответе они идут с приставкой (`group_collaborator.collaborator_id`), в условиях и в `fields` их пишут без неё: `collaborator_id`.
- Документа у строки нет: `id` строки не читается через `hcm_object_get`. Чтобы строка изменилась, правят документ, из которого она построена.
- После удаления документа сервер 2025.2 на PostgreSQL такие строки не убирает: строки удалённой группы остаются в `group_collaborators`, строки удалённых сотрудника и должности — в `person_hierarchys`. На MS SQL и на 2025.1 они исчезают. Объект, на который ссылается строка, проверяй по его собственному каталогу.

У нескольких типов каталога нет вовсе (`user_data`): в ответе `hcm_types` у них нет поля `catalog`. Сколько каталогов на сервере всего, вместе с каталогами без своего типа, говорит `catalogs` в том же ответе. Общие списки сервера (`common.event_types`) — не каталоги: `hcm_query` по ним не ищет, их элементы читает `hcm_xquery {query:"for $e in common.event_types return $e"}`.

## Запрос XQuery

`hcm_xquery` нужен, когда `hcm_query` мало: «или», связи каталогов, функции. Требует права `execute`. Запрос должен возвращать строки каталога целиком (`return $e`), поля выбирает аргумент `fields`.

```json
{ "query": "for $e in collaborators where $e/is_dismiss = false() order by $e/fullname descending return $e", "fields": ["id", "fullname"], "limit": 20 }
```

Проверенные формы условий:

```
$e/is_dismiss = false()
contains($e/fullname, 'Иван') or $e/login = 'user1'
$e/hire_date >= date('2024-01-01')
$e/id = 0x5555555555555501
MatchSome($e/id, (0x5555555555555501, 0x5555555555555502))
MatchSome($e/role_id, (0x5555555555555501))
$e/code = ''
($e/role_id = '' or IsEmpty($e/role_id) = true())
IsEmpty($e/email) = false()
for $e in collaborators, $s in subdivisions where $e/position_parent_id = $s/id return $e
```

Значение пишется по типу поля. Иначе запрос ничего не находит или его отвергает база данных, а ошибки сервер не даёт:

- ID — без кавычек: `0x5555555555555501` или десятичной записью. ID в кавычках (`'0x…'`) база отвергает.
- Дата — только через `date('…')`. Дату строкой в кавычках MS SQL принимает, а PostgreSQL отвергает.
- Поле со списком значений (в строке оно приходит списком) сравнивай через `MatchSome`. Равенство с ID в записи `0x…` на MS SQL ничего не находит. Пустой список ищет форма с `IsEmpty` из примеров выше: одно `= ''` на PostgreSQL ничего не находит.
- Строки на PostgreSQL сравниваются с учётом регистра, на MS SQL — без.
- Функций `starts-with`, `StrBegins`, `matches` в запросе нет. Незнакомую функцию сервер передаёт базе данных как есть, поэтому `like($e/code, 'mt-%')` работает только на PostgreSQL, а `substring($e/code, 1, 3) = 'mt-'` — только на MS SQL.

Когда сервер отвергает запрос, клиент сверяет каталоги и поля, названные в его тексте: `UNKNOWN_CATALOG` и `UNKNOWN_CATALOG_FIELD` приходят так же, как у `hcm_query`.

Отвергнутый запрос отличается от пустого ответа: в нём `incomplete:true` и нет `total`. Причину база пишет в лог `spxml_unibridge` рядом с текстом запроса, см. [logs.md](logs.md). Страницы и ответ такие же, как у `hcm_query`.

## Что изменилось и сколько записей

- Изменённые и новые объекты: `hcm_query {catalog:"groups", where:{modification_date:{gte:"2026-10-04T19:00:00"}}, fields:["id","code","modification_date"]}`. Запрос идёт по одному каталогу; поле `modification_date` есть почти в каждом. Время — местное серверное.
- По всем типам сразу: каталоги взять из `hcm_types {limit:1000}`, запросы слать пакетами по 100 шагов (`runtime.batch`, `stopOnError:false`). Каталог без `modification_date` ответит `UNKNOWN_CATALOG_FIELD` — пропусти его; шаг с `incomplete:true` — отвергнутый запрос, а не «изменений нет».
- Число записей: `total` в ответе `hcm_query` с `limit:1`.
- Удалённых объектов в каталоге нет, поиском их не найти.
- Операции `native.lds.getModObjects` и `getCatalogsStat` из `hcm_api_list` на проверенных серверах отвечают пусто. Рассчитывать на них нельзя.

## Ошибки

| Код | Что случилось | Что делать |
| --- | --- | --- |
| `UNKNOWN_CATALOG` | такого каталога нет | взять имя из `hint` или из `hcm_types` |
| `UNKNOWN_CATALOG_FIELD` | поля нет в каталоге | выбрать поле с `query:true` либо прочитать документ через `hcm_object_get` |
| `INVALID_FILTER_OPERATOR` | неизвестный оператор | использовать перечисленные выше |
| `QUERY_REPRESENTATION` | запрос XQuery вернул не строки каталога | закончить запрос на `return $e` |
| `PLATFORM_SOAP-FAULT`, HTTP 500 | сервер отверг запрос XQuery, а каталоги и поля в нём названы верно | сверить запрос с формами выше; строка в логе `xhttp` бывает не всегда, см. [logs.md](logs.md) |
| `INVALID_FILTER_VALUE` | значение условия — не строка, число, `true`, `false` или `null` | ID передать строкой |

Пустой ответ с `total: 0` — это «ничего не найдено». Пустой ответ с `incomplete:true` и без `total` — запрос отвергла база данных, см. выше.

# Логи сервера

Логи читаются через API сервера, доступ к его диску не нужен. Права `write` и `execute` не требуются.

## Найти причину отказа

Сервер на отказ отвечает HTTP 500 без объяснения. Строку об отказе он пишет в главный лог — `xhttp_ГГГГ-ММ-ДД.log` за сегодняшнюю дату сервера.

1. `hcm_logs_list {type:"xhttp"}` — взять имя файла; новые файлы идут первыми.
2. `hcm_logs_follow {file:"xhttp_2026-10-01.log"}` — последние 10 событий. Строка об отказе — среди них.
3. Старые события ищет `hcm_logs_search {file:"xhttp_2026-10-01.log", level:"error", limit:5}` или поиск по тексту: `text:"XQUERY FAILED"`.

Строка бывает подробной, а бывает короткой и без имени объекта:

```
XQUERY FAILED: for $elem in webinar_systems … - 'webinar_systems' not defined
unibridge error: Недопустимое имя объекта "dbo.no_such_catalog"
Error evaluating collection 'hcm_inline_…'  — ошибка кода из hcm_script, имя совпадает с executionId
Unknown method: no_such_method
Элемент не найден          — объекта или файла по этому адресу нет
Неизвестная ошибка
```

Насколько подробна строка, зависит от версии сервера. Ошибка в тексте запроса XQuery может не оставить в логе `xhttp` ничего: тогда проверь сам запрос, см. [queries.md](queries.md).

У одного запроса метка `context` в логах `xhttp` и `spxml_unibridge` одна. Если в `xhttp` только короткая строка («Неизвестная ошибка»), возьми её `context` и найди подробности: `hcm_logs_search {file:"spxml_unibridge_2026-10-01.log", context:"…"}`. Так же после `UNKNOWN_CATALOG`.

Запрос, который отвергла база данных (ответ `hcm_query` или `hcm_xquery` пуст и с `incomplete:true`), записан в логе `spxml_unibridge_ГГГГ-ММ-ДД.log`. Сразу после запроса вызови `hcm_logs_follow {file:"spxml_unibridge_2026-10-01.log"}`: среди последних событий будет ошибка базы, а под ней строки `XQuery:` с текстом запроса и `SQL:` с тем, что из него получилось.

```
Error: Ошибка при преобразовании типа данных varchar к bigint.          — MS SQL: ID в кавычках
Error: 42883: оператор не существует: timestamp without time zone >= character varying   — PostgreSQL: дата в кавычках
```

## Инструменты

| Инструмент | Что делает |
| --- | --- |
| `hcm_logs_list` | файлы: имя, тип, дата, размер; сначала новые, 30 на странице. Тип — имя файла без даты: `xhttp`, `xhttp_middleware`, `agent`. Фильтры: `type`, `nameContains`, `startDate`, `endDate` |
| `hcm_logs_read` | текст: по умолчанию конец файла, сколько помещается в ответ. `tailBytes` — взять больше, `full:true` — весь файл |
| `hcm_logs_search` | события по `text`, `level`, `context`; многострочное событие (со стеком) приходит целиком. `newestFirst:true` — сначала последние |
| `hcm_logs_follow` | что появилось с прошлого вызова |

Поиск идёт по концу файла (512 КБ). Чтобы искать по всему файлу, добавь `full:true`. `totalEvents` в ответе — сколько событий в прочитанной части; `tailOnly:true` — прочитан только конец файла, и счёт идёт не по всему файлу; `tailOnly:false` — файл прочитан целиком.

Что в каком логе:

| Лог | Что в нём |
| --- | --- |
| `xhttp` | главный: отказы сервера, ошибки кода из `hcm_script`, строки, которые код пишет через `alert`. Запрос, который сервер выполнил, строки не оставляет |
| `spxml_unibridge` | ошибки базы данных с текстом запроса XQuery и SQL; файлы `spxml_unibridge_none_<номер>_<дата>` — тот же лог отдельных процессов сервера, все вместе показывает `hcm_logs_list {nameContains:"spxml_unibridge"}` |
| `agent` | запуски агентов сервера и их ошибки |
| `auth-events` | входы и выходы пользователей: `login LDS user1 <адрес>`. Строка об удалении (`delete_user LDS user1 wt_data`) называет пользователя и базу, но не объект: что именно удалено, логи не скажут |
| `email` | отправка уведомлений |
| `xhttp_middleware`, `dotnetcore`, `components`, `package_manager` (на 2025.1 — `pakage_manager`), `licensing`, `lucene` | запуск сервера и его частей. Последний запуск — последняя строка `Starting in Normal Mode` в `dotnetcore`: файл за день запуска, поиск с `full:true` и `newestFirst:true` |

Набор логов зависит от версии и настроек сервера: точные имена показывает `hcm_logs_list`.

Прочитанный текст сохраняется локально, в ответе `meta.resultId`; от текста, который не поместился (`tailBytes`, `full:true`), в ответе только начало. `hcm_result_read {resultId}` читает его частями как текст, `hcm_result_export {resultId, path, format:"text"}` сохраняет в файл. Весь лог в файл: `hcm_logs_read {file:"…", full:true}` и экспорт по его `meta.resultId`. Текст сохраняется в UTF-8 со знаком BOM и концами строк LF: размер файла меньше `sizeBytes` на сервере на число строк; `fingerprint` считается по этому тексту.

Ответ поиска: `events` (у каждого `time`, `context`, `level`, `text`), `matches` — сколько совпадений всего. В файле строка записана как `время [context] текст`; `text` — она же без времени и метки: для цитаты читать файл заново не нужно. Пока есть `nextOffset`, совпадения не кончились: повтори вызов с `offset: nextOffset` и `expectedFingerprint: fingerprint` из ответа. `cutBySize:true` значит, что на странице меньше событий, чем просил `limit`: больше не поместилось в один ответ (событие со стеком бывает длинным). `LOG_CHANGED` значит, что лог за это время дописан: начни поиск заново.

`level` определяется по словам в тексте события, русским и английским, приблизительно. Счёт по `level:"error"` может быть занижен; если ошибок по нему нет, ищи по тексту.

Время в логе — время сервера. Сколько на сервере сейчас: `hcm_script {code:"RESULT = [StrDate(Date())];"}`.

После каждой записи в лог сервер несколько секунд не отдаёт этот файл. Клиент сам пережидает это время, поэтому чтение лога сразу после отказа может занять около шести секунд. Повторять вызов в цикле не нужно: отказ в чтении сервер тоже пишет в лог, и ожидание начинается заново.

## Своя строка в логе

Код на сервере пишет в лог сам. Так проверяют, что код дошёл до нужного места:

- `alert('текст')` и `LogEvent('', 'текст')` — строка в `xhttp`;
- первый аргумент `LogEvent` — имя лога, а не уровень. `LogEvent('info', 'текст')` пишет в лог `info`, которого нет: строка пропадает без ошибки;
- свой лог сначала включают: `EnableLog('my_log', true); LogEvent('my_log', 'текст');` — на сервере появится файл `my_log_ГГГГ-ММ-ДД.log`.

## Следить за логом

1. Первый вызов `hcm_logs_follow {file:"…"}` отдаёт последние 10 событий и `cursor`.
2. Выполни действие, которое проверяешь.
3. `hcm_logs_follow {file:"…", cursor:"…"}` отдаёт то, что появилось. Возьми новый `cursor` из ответа.

Последнее событие может прийти повторно, если его дописали. `omitted:N` — столько новых событий не поместилось в ответ, прочитай их поиском. `gapPossible:true` — часть событий могла быть пропущена: прочитай конец файла через `hcm_logs_read`.

Каждый день сервер начинает новый файл. Для нового файла начни без `cursor`.

## Ошибки

| Код | Что случилось | Что делать |
| --- | --- | --- |
| `LOG_READ_UNAVAILABLE` | сервер не отдал текст файла и со второй попытки: в лог всё время пишут | повторить через десять секунд или взять лог за прошлую дату; обходить через код не нужно |
| `LOG_NOT_FOUND` | файла с таким именем в списке нет | взять имя из `hcm_logs_list` |
| `LOG_CHANGED` | файл изменился между страницами | начать чтение заново |
| `INVALID_LOG_CURSOR` | курсор от другого файла или испорчен | начать без `cursor` |

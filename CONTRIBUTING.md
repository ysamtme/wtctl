# Как сообщить об ошибке и предложить изменение

Проект в альфа-версии. Сообщения об ошибках, пожелания и pull request принимаются, но ответ, исправление и новые возможности по запросу не обещаны.

## Сообщить об ошибке

Issue можно писать по-русски или по-английски. Что приложить:

- версию клиента: `wtctl version`;
- версию сервера и базу данных: поля `version` и `database` из `wtctl status`;
- интерфейс: MCP-сервер, CLI или SDK; для MCP-сервера — приложение и его версию;
- команду или вызов инструмента и ответ: `error.code`, `message`, `hint`;
- вывод `wtctl check`, если не работает подключение.

Перед отправкой из текста нужно убрать пароли, адреса серверов, имена людей и другие данные с сервера. Пароль из текстов ошибок клиент убирает сам, но содержимое объектов и логов в ответах остаётся.

Об уязвимостях пишут не в issue: [SECURITY.md](SECURITY.md).

## Предложить изменение

Перед крупным изменением лучше сначала открыть issue и описать, что предлагается.

```shell
npm ci
npm run verify
```

`npm run verify` должен проходить: формат, типы, тесты, проверка документации и пакета. Тестам сервер не нужен: его ответы в них заданы заранее.

Что нужно знать:

- Язык проекта — русский: тексты для пользователя и агента, документация, сообщения коммитов.
- SDK, CLI и MCP-сервер только разбирают ввод и показывают ответ. Запросы к серверу, проверка прав и логика операций лежат в `src/runtime.ts`, `src/native/` и `src/protocol/`: [как устроен клиент](docs/architecture.md).
- Тексты гайда правятся в `skills/wtctl/`, справочник SDK `docs/sdk-reference.md` — в описаниях типов в `src/`; после правки нужен `npm run generate`.
- Клиент ничего не устанавливает на сервер и не обходит его отказы.
- Штатные файлы сервера — формы, библиотеки, языковые файлы — в репозиторий не копируются ни целиком, ни кусками.
